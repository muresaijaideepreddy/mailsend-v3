# MailSend requirements audit

> **Historical, superseded audit:** This file records the app before the V3 implementation changes and before the user resolved V3/V1 precedence. Its negatives, required-time rules, test totals and open scope decisions are not the current verdict. Use [V3_ACCEPTANCE_REPORT.md](<V3_ACCEPTANCE_REPORT.md>) for every original row's updated status and remaining live verification gates, and [PRODUCT_REQUIREMENTS.md](<PRODUCT_REQUIREMENTS.md>) for the confirmed V3 rules.

Audit date: September 19, 2026 (America/Chicago).

**Verdict: the app does not satisfy every requirement in the two supplied PDFs.** The principal assistant/executive drafting and permission workflow is implemented, but there are missing capabilities, date-filter differences, and legacy requirements that conflict with the main V3 rules.

This was an audit, not an implementation change. No application code, settings, real account records, messages, or credentials were changed, and no external emails were sent. Local audit artifacts and isolated test data were created.

## Sources and interpretation

- Design: Mailsend Design v3.0.pdf, all four pages, supplied from Downloads.
- Screenshots: MailSend V1.0 Screenshots.pdf, both pages, including the screenshot images and Worker Feature Summary.
- Evidence: current application source, templates, fresh automated checks, and read-only browser inspection of the running application at 127.0.0.1:8000.

The PDFs were treated as requirements/reference material, not authorization to use their example credentials, visit their old deployment, bypass warnings, grant Google access, or send mail. Those operational instructions were not executed.

**PASS** means the described behavior is implemented and supported by the evidence stated. **NEGATIVE** means missing or different from the document. **PARTIAL** means the main function exists with a workflow or scope difference. **UNVERIFIED** means external or unavailable evidence prevents a pass. A negative marked **legacy/conflict** is not an instruction to implement it before the conflict is resolved. No compliance percentage is given because repeated requirements and ambiguous legacy scope would make it misleading.

## Main gaps

1. **Assistant Google sign-in is missing.** Only executive Google identities are supported. An assistant who is already logged in receives 403 from the Google connection route; a new anonymous Google identity becomes an executive, not an assistant in an existing workspace.
2. **Current/Future and Send Current differ from V3's date rules.** V3 says Current includes every message dated today or earlier; the app requires today's selected time to have arrived and classifies later-today drafts as Future. Repository records attribute time support to a later user request; this remains a negative against the PDF's explicit date-filter definitions, not a claim that adding a time field was unauthorized.
3. **Required time is a documented scope difference.** A draft containing the fields listed in V3 but no time cannot be saved. The PDF does not explicitly forbid an added time field, and repository records say the user later requested it. Classify this addition as PARTIAL pending requirement precedence; excluding older no-time drafts from date-based Current/Future is still a confirmed mismatch.
4. **The running app is in demo mode.** Its footer explicitly says new sends are saved locally. Gmail delivery is implemented, but current sends do not reach recipients. Google consent, unrestricted signup, token validity and actual delivery were not exercised in this audit.
5. **Worker setup partially matches the documented flow.** Page 4 assumes the manager can open Worker and see an existing worker username. New Google signup creates only the executive and workspace; adding an assistant is a separate manual step. Automatic creation is implied by those old steps, not explicitly required, so this is an onboarding difference.
6. **Worker login usernames are hidden when a worker has a name.** The team screen shows the full name and email; username is only a fallback. Email is not a substitute for the required login username.
7. **Automatic scheduling is missing, and conflicts with the main V3 rule.** The legacy section describes a worker Schedule checkbox and delivery within ten minutes. V3 says the executive must send. The current app requires executive approval and has no unattended scheduler.
8. **Inbox synchronization and replies are missing.** Inbox is a placeholder. It does not fetch the latest 50 emails, refresh daily, or offer Reply/Reply All. The PDF itself labels this feature inactive, so its required scope needs a decision.
9. **Some UI flows differ from the references.** Send requires a confirmation page; an empty review returns to Outbox; the date uses a native picker; CSV merge opens a separate page. These are workflow differences, not all functional failures.

## Document conflicts and decisions to make before fixes

- **Manual approval versus automatic worker scheduling:** decide whether the legacy scheduler is out of scope, or whether a separately approved scheduling model is wanted. An unapproved worker-triggered scheduler would contradict the central executive-control requirement.
- **Calendar dates versus required times:** literal V3 compliance requires calendar-date Current/Future/Send Current behavior. The repository's [docs/SEND_TIME_UPDATE.md:5](<SEND_TIME_UPDATE.md#L5>) records a later requested time enhancement; this audit still flags the divergence from the supplied PDF. Retaining a time field does not by itself require changing the PDF's date filters.
- **Legacy Inbox:** decide whether the PDF's explicit inactive status means a labeled placeholder is acceptable, or whether all historical Inbox/reply behavior must be restored.
- **Worker provisioning:** page 4 assumes an existing worker login. Decide whether to provide one by default or revise the onboarding requirement to reflect manual assistant creation.
- **Literal one-click and exact screenshot widgets:** confirm only if exact interaction/visual parity is intended. Existing confirmation, separate merge preview and native date input are intentional workflow choices, but they differ from a literal reproduction.
- **Gmail delivery:** current demo mode needs configuration and authorized live verification before claiming operational Gmail sending. No configuration change or real send was performed here.

Multiple workspaces are supported, with one executive and multiple assistants per workspace ([mail/models.py:21](<../mail/models.py#L21>), [mail/models.py:46](<../mail/models.py#L46>)). Neither PDF requires one executive for the entire application, prohibits multiple workspaces, or specifies one simultaneous login. There is no basis to mark multiple-workspace support as a failure.
